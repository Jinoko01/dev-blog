# 프론트엔드 코드 품질 기준

코드 작성·수정·리뷰에서 가독성, 예측 가능성, 응집도, 결합도를 점검한다. 기준이 충돌하면 이번 변경을 이해하고 안전하게 수정하는 데 더 중요한 쪽을 선택하고, 그 이유를 짧게 남긴다.

이 문서는 [토스 Frontend Fundamentals](https://frontend-fundamentals.com/code-quality/code/)의 네 가지 기준을 이 프로젝트에 적용한다. 구체적인 작업 순서는 [프론트엔드 변경 가이드](frontend_clean_code_guide.md), 데이터 흐름은 [블로그 API 가이드](api-guide.md)를 참고한다.

## 가독성

코드를 읽는 사람이 렌더링 위치, 데이터 출처, 상태별 화면을 쉽게 파악할 수 있어야 한다.

- App Router의 페이지·레이아웃은 Server Component를 기본으로 검토한다. 이벤트·브라우저 API·상태 훅이 필요한 경계에만 Client Component를 둔다.
- 로딩, 데이터 없음, 오류, 정상 상태를 구분한다. 중첩 삼항 연산자나 겹치는 조건 때문에 표시할 화면이 불분명해지지 않게 한다.
- 복잡한 조건과 도메인 의미가 있는 값에는 이름을 붙인다. 영어 식별자와 주변 코드의 명명 규칙을 유지한다.
- 함수를 따라가야만 핵심 동작을 알 수 있도록 잘게 쪼개지 않는다. 화면의 주요 흐름과 간단한 목록 렌더링은 읽기 쉬우면 함께 둔다.
- `Suspense` 경계와 fallback에서 어느 콘텐츠를 기다리는지 드러낸다. 큰 페이지 전체를 클라이언트로 바꿔 서버 렌더링의 복잡성을 숨기지 않는다.

현재 [홈 페이지](../apps/web/src/app/page.tsx)는 데이터 조회와 대기 화면의 경계를 드러낸다. [ArticlesClient](../apps/web/src/components/articles-client.tsx)는 검색·필터 조작과 결과 표시를 담당한다. 수정할 때 이 역할을 먼저 확인한다.

## 예측 가능성

함수의 이름·타입·호출 위치에서 반환값과 부작용을 예상할 수 있어야 한다.

- 같은 계층의 API 함수는 성공·실패 계약을 일관되게 유지한다. 다른 계층에서 의도적으로 변환하는 값은 호출자가 알 수 있게 한다.
- 공개 블로그의 HTTP 오류는 `ApiError`다. 서버 캐시의 `getPost`가 404를 `null`로 바꾸는 계약과 관리자 API가 `Error`를 던지는 계약을 구분한다.
- DTO를 화면 모델로 바꾸는 함수에 방문 기록, 캐시 갱신, 전역 상태 변경을 섞지 않는다.
- 좋아요 토글, 조회수 기록, 관리자 저장처럼 부작용이 있는 작업은 호출부에서 목적이 드러나야 한다.
- 서버 캐시 재검증과 화면 상태 갱신을 구분한다. 서버 태그를 무효화했다고 해서 Query 캐시나 Jotai 상태까지 자동으로 바뀐다고 가정하지 않는다.
- 공개 캐시에 개인별 응답을 섞지 않는다. 인증 확인과 권한 검사는 UI의 표시 여부와 별개로 검토한다.

응답 변환과 캐시 계약은 [web의 api.ts](../apps/web/src/lib/api.ts)와 [api.server.ts](../apps/web/src/lib/api.server.ts)에 나뉘어 있다. 이 분리를 유지하면서 변경 범위를 판단한다.

## 응집도

함께 바뀌는 데이터, 조건, 상태 전이를 가까운 곳에서 관리한다.

- 새 파일은 먼저 해당 앱의 기존 `app`, `components`, `lib`, `store` 구조에 맞춘다. 폴더 규칙을 맞추기 위한 전체 이동은 하지 않는다.
- 특정 화면에서만 사용하는 조회 옵션·타입·보조 함수는 사용 위치 가까이에 둔다. 반복 사용이 확인될 때 공유 범위를 넓힌다.
- 캐시 수명과 태그는 관련 서버 조회 함수에서 함께 확인할 수 있게 한다. 클라이언트 staleTime과 서버 재검증 간격은 역할을 구분해 관리한다.
- 폼의 검증, 제출 상태, 저장 결과처럼 함께 바뀌는 동작은 폼 단위로 묶는다. 필드마다 별도 상태 관리 계층을 만들지 않는다.
- 좋아요 수·선택 여부·요청 중 상태처럼 하나의 사용자 동작에 따라 바뀌는 값은 같은 상태 전이 안에서 처리한다.

현재 [게시글 반응 상태](../apps/web/src/store/post-metrics.ts)는 좋아요 상태와 실패 복구를 함께 관리한다. [PostForm](../apps/admin/src/components/post-form.tsx)을 수정할 때도 입력·업로드·저장이 함께 바뀌는 범위를 확인한다.

## 결합도

한 기능의 변경이 무관한 화면이나 실행 환경으로 퍼지지 않게 한다.

- 서버 전용 API와 브라우저 상태의 의존성을 분리한다. Client Component에서 `api.server.ts`를 가져오지 않는다.
- 공개 블로그와 관리자 앱의 인증·오류 처리는 다르다. 파일 모양이 비슷하다는 이유만으로 하나의 범용 클라이언트로 합치지 않는다.
- 컴포넌트의 책임은 줄이되, 책임 하나당 반드시 파일 하나를 만들지는 않는다. 변경 이유가 같은 코드인지 먼저 판단한다.
- props 전달이 불편하다는 이유만으로 전역 상태를 추가하지 않는다. 상태를 실제 사용하는 범위와 컴포넌트 합성을 먼저 확인한다.
- 여러 앱에서 같은 의미로 쓰는 코드만 공유 패키지로 옮긴다. 기존 [MDX 렌더러](../packages/mdx-renderer/package.json)는 두 앱이 함께 쓰는 렌더링 기능을 담는다.
- 스타일링은 Tailwind CSS와 프로젝트의 테마 토큰을 사용한다. 특정 화면의 스타일을 위해 무관한 전역 규칙을 바꾸지 않는다.

## 변경 전후 점검

- 변경할 동작과 유지할 동작을 구분했는가.
- 서버·클라이언트·캐시 경계가 코드에서 드러나는가.
- 데이터 없음, 요청 실패, 권한 부족을 같은 상태로 처리하지 않는가.
- 함께 변경되는 상태와 실패 복구가 같은 위치에 있는가.
- 공통화로 늘어나는 옵션·분기보다 실제 중복 제거의 이점이 큰가.
- 새 추상화나 의존성 없이 더 작게 해결할 수 없는가.
- 검증한 결과와 아직 확인하지 못한 항목을 구분해 보고했는가.
