# 프론트엔드 변경 가이드

공개 블로그와 관리자 앱에서 필요한 동작만 수정하고 검증하는 절차를 정리한다. 현재 구현과 새로 제안하는 설계를 구분하고, 코드 길이보다 변경 이유와 영향 범위를 기준으로 판단한다.

기존 문서가 참고한 토스 SLASH 21의 「실무에서 바로 쓰는 Frontend Clean Code」(진유림)의 응집도·단일 책임·추상화 원칙을 이 프로젝트의 작업 기준으로 정리했다. 품질 기준은 [프론트엔드 코드 품질 기준](frontend-code-quality.md), 통신 계약은 [블로그 API 가이드](api-guide.md)에서 다룬다.

## 프로젝트 구조 확인하기

이 저장소는 pnpm과 Turborepo를 사용하는 모노레포다. 두 앱은 Next.js 16.2.0, React 19.2.4, TypeScript strict, Tailwind CSS v4를 사용한다.

| 위치                                                           | 책임                                                       |
| -------------------------------------------------------------- | ---------------------------------------------------------- |
| [apps/web](../apps/web/package.json)                           | 공개 블로그의 게시글·알고리즘 조회, 검색, 방문·좋아요 반응 |
| [apps/admin](../apps/admin/package.json)                       | 관리자 로그인, 콘텐츠 편집·발행, 이미지 업로드             |
| [packages/mdx-renderer](../packages/mdx-renderer/package.json) | 두 앱에서 사용하는 MDX 렌더링 컴포넌트와 설정              |
| [scripts](../scripts)                                          | 루트 테스트 스크립트                                       |

페이지와 레이아웃은 각 앱의 `src/app`, 화면 구성 요소는 `src/components`, API와 변환 로직은 `src/lib`에서 찾는다. 공개 블로그의 공유 반응 상태는 `src/store`에 있다.

백엔드 구현은 이 저장소에 없다. 프론트엔드에서 확인한 요청 계약을 서버 구현의 보장으로 확대하지 않는다. 새 라이브러리의 사용 여부는 설치된 의존성과 실제 호출부를 모두 확인한다.

## 변경 범위 정하기

1. 바뀌어야 할 사용자 동작과 그대로 유지할 동작을 적는다.
2. 해당 페이지에서 컴포넌트, API 함수, 상태 저장소까지 호출 흐름을 확인한다.
3. 데이터 모델·인증·캐시·공유 패키지 중 영향을 받는 경계를 고른다.
4. 재현 방법과 완료를 판단할 검증 방법을 정한다.
5. 기존 작업 내용과 이번 수정 파일을 구분한다. 관련 없는 정리나 파일 이동을 묶지 않는다.

추상화는 반복되는 변경 이유가 확인되었을 때 추가한다. 한 번 사용하는 로직을 숨기기 위해 훅이나 범용 컴포넌트를 만들지 않는다. 단순한 조건 분기와 목록 렌더링은 읽기 쉬우면 그대로 둔다.

핵심 업무 흐름은 호출 위치에서 드러나야 한다. 저장·업로드·인증·통계 기록을 의미 없는 이름의 함수 안에 숨기지 않는다. 보조 함수를 분리하더라도 주변 코드의 영어 식별자와 명명 규칙을 따른다.

## 렌더링과 상태 경계 유지하기

두 앱 모두 Cache Components를 활성화했다. 공개 데이터 캐시와 요청별 동작을 구분하고, 브라우저 상태를 서버 캐시와 혼동하지 않는다.

| 데이터·동작                | 현재 담당 위치                              | 수정할 때 확인할 점                                   |
| -------------------------- | ------------------------------------------- | ----------------------------------------------------- |
| 공개 페이지의 초기 데이터  | Server Component와 web의 `api.server.ts`    | 캐시 대상, 함수 인자, 태그, 재검증 간격               |
| 검색·태그·정렬·페이지 조작 | ArticlesClient의 로컬 상태와 TanStack Query | 조회 조건별 키, 초기 데이터 적용 조건, 이전 결과 표시 |
| 게시글 좋아요              | Jotai의 게시글 반응 상태                    | slug별 공유 범위, 중복 요청 방지, 실패 시 복구        |
| 관리자 데이터와 폼         | 관리자 컴포넌트의 로컬 상태·Effect·API 함수 | 인증 만료, 로딩·오류 표시, 제출·업로드 상태           |
| 두 앱의 MDX 표현           | 공유 MDX 렌더러와 각 앱의 호출부            | 공개 화면과 관리자 미리보기에 미치는 영향             |

새 페이지는 Server Component를 먼저 검토하고, 상호작용이 필요한 부분에 Client Component를 둔다. 서버의 초기 조회를 불필요하게 Effect로 옮기지 않는다. 반대로 기존 Effect가 브라우저 저장소 동기화나 클라이언트 요청에 쓰인다면 목적을 확인한 뒤 수정한다.

요청 시점의 데이터와 동적 처리는 적절한 `Suspense` 경계 아래에 둔다. fallback은 사용자가 무엇을 기다리는지 알 수 있어야 한다. 기존 캐시 함수에는 공개 콘텐츠만 넣고, 인증 토큰이나 개인별 데이터가 섞이는지 확인한다.

관리자 앱의 Cache Components 설정은 관리용 응답을 공유 캐시에 넣는다는 뜻이 아니다. 현재 관리자 데이터 요청은 브라우저의 인증 흐름을 따른다. 쿠키 인증, Server Action, TanStack Query로의 전환은 별도의 설계 변경으로 다룬다.

## 화면과 공통 코드 수정하기

- 스타일은 Tailwind CSS와 해당 앱의 테마 토큰을 사용한다. 기존 전역 스타일을 바꿀 때는 영향을 받는 화면을 함께 확인한다.
- 네비게이션과 이미지 렌더링은 Next.js의 기존 구현을 확인하고 이어서 사용한다.
- 버튼·링크·폼의 의미, 접근 가능한 이름, 키보드 조작, 포커스 표시를 유지한다.
- 새로운 전역 상태를 만들기 전에 로컬 상태나 컴포넌트 합성으로 해결할 수 있는지 확인한다.
- 공통 패키지 수정은 두 앱을 대상으로 검증한다. 시각적으로 비슷하다는 이유만으로 다른 업무의 컴포넌트를 합치지 않는다.
- 이번 수정 때문에 쓰이지 않게 된 import나 변수만 정리한다. 관련 없는 기존 코드를 함께 삭제하지 않는다.

## 변경 결과 검증하기

아래 명령은 루트와 각 앱의 `package.json`에 정의된 스크립트를 기준으로 한다. 명령이 존재한다는 사실과 검증을 통과했다는 사실을 구분한다.

| 명령                  | 실행 위치          | 확인할 내용                                                              |
| --------------------- | ------------------ | ------------------------------------------------------------------------ |
| `pnpm lint`           | 저장소 루트        | 두 앱의 ESLint 검사                                                      |
| `pnpm test`           | 저장소 루트        | `scripts/*.test.mjs`의 Node.js 테스트                                    |
| `pnpm build`          | 저장소 루트        | 두 Next.js 앱의 프로덕션 빌드                                            |
| `pnpm test-storybook` | 변경한 앱 디렉토리 | Vitest 브라우저 환경의 Storybook 테스트                                  |
| `pnpm format`         | 저장소 루트        | TS·TSX·Markdown 포맷 정리. 실행 후 관련 없는 변경이 생기지 않았는지 확인 |

코드를 작성하거나 수정하면 `pnpm lint`를 실행한다. 서버·캐시·라우팅을 바꾸면 빌드에서도 확인한다. 동작을 바꿨다면 해당 흐름을 검증하고, 회귀 위험이 있는 로직에는 필요한 테스트를 추가한다. 문서만 바꿨다면 문서 포맷, 링크, 실제 구현과의 일치를 확인한다.

루트의 `pnpm test`는 전체 UI나 백엔드 통합을 검증하지 않는다. Storybook 테스트도 전체 서비스의 E2E 테스트를 대신하지 않는다. 현재 `test:e2e` 스크립트는 없으므로, 존재하지 않는 명령을 실행했거나 통과했다고 보고하지 않는다. PR을 올리기 전에는 변경 범위에 맞는 테스트를 수행한다.

캐시를 바꿀 때는 입력별 응답 분리, 재사용, 변경 성공 후 갱신, 변경 실패 시 기존 상태 유지, 데이터 없음과 오류를 확인한다. 인증·업로드를 바꿀 때는 로그인 만료와 업로드 실패를 포함한다. 실제 백엔드 연결 여부와 확인하지 못한 흐름을 함께 기록한다.

## 변경 내용 보고하기

결과에는 바뀐 동작, 변경 이유, 실행한 검증, 남은 제약을 적는다. 확인하지 못한 사항은 추정으로 채우지 말고 미확인 또는 TBD로 표시한다.

커밋을 요청받으면 검증한 작업 단위로 관련 파일만 포함한다. 커밋 메시지는 프로젝트 규칙에 따라 영어 Conventional Commits 형식으로 작성한다. 기존 사용자 변경과 파일 삭제 내역을 임의로 포함하지 않는다.
