# 블로그 API 가이드

공개 블로그와 관리자 앱의 API 호출 위치, 응답 처리, 캐시 갱신 흐름을 설명한다. 새 API를 추가하거나 기존 요청을 수정할 때 이 문서에서 영향을 받는 경계를 확인한다.

이 문서는 저장소의 프론트엔드 구현을 기준으로 한다. 백엔드 구현은 이 저장소에 없으므로 서버 내부의 인증·저장 정책은 여기서 보장하지 않는다.

## API 호출 경로

두 앱은 Next.js 16 App Router를 사용하며, HTTP 요청은 내장 `fetch`로 처리한다.

| 실행 위치                      | 담당 파일                                                          | 현재 동작                                                                        |
| ------------------------------ | ------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| 공개 페이지의 Server Component | [web의 api.server.ts](../apps/web/src/lib/api.server.ts)           | 캐시 정책을 적용한 뒤 공통 API 함수를 호출한다.                                  |
| 공개 블로그의 공통 요청        | [web의 api.ts](../apps/web/src/lib/api.ts)                         | 서버에서는 백엔드에 직접 요청하고, 브라우저에서는 같은 출처의 `/api`로 요청한다. |
| 공개 블로그의 Route Handler    | [web의 API 라우트](../apps/web/src/app/api/%5B...path%5D/route.ts) | 브라우저의 GET·POST·DELETE 요청을 백엔드로 전달한다.                             |
| 관리자 앱                      | [admin의 api.ts](../apps/admin/src/lib/api.ts)                     | 백엔드에 직접 요청한다. 관리용 요청에는 Bearer 토큰을 추가한다.                  |

공개 블로그 서버의 백엔드 주소는 `API_BASE_URL`을 사용하며, 미설정 시 `http://localhost:8080`으로 연결한다. 브라우저에 이 서버 환경 변수를 노출하지 않는다.

관리자 앱은 `NEXT_PUBLIC_API_BASE_URL`을 우선 사용한다. 브라우저에서 직접 요청하므로 이 공개 환경 변수가 필요하다. 서버에서 사용하는 `API_BASE_URL`만 설정해도 브라우저에 전달되는 것은 아니다. 공개 환경 변수에 비밀값을 넣지 않는다.

## 응답과 오류 처리

DTO(Data Transfer Object)는 API 응답의 형태를 나타낸다. 화면에서 필요한 모델로 바꾸는 작업은 각 앱의 API 모듈에서 수행한다. 공개 블로그의 `toPostMetadata`·`toArticleListItem`, 관리자 앱의 `toAdminPost`·`toAdminAlgorithm`이 이 역할을 맡는다.

| 경계                              | 성공 처리                                                                              | 실패 처리                                                                                          |
| --------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 공개 블로그의 `api.ts`            | JSON을 읽고 필요한 모델로 변환한다. HTTP 204는 `undefined`를 반환한다.                 | HTTP 오류는 상태 코드를 가진 `ApiError`를 던진다. 네트워크 오류를 같은 타입으로 변환하지는 않는다. |
| 공개 블로그의 캐시 함수 `getPost` | 게시글을 반환한다.                                                                     | HTTP 404만 캐시 함수 안에서 `null`로 바꾼다. 다른 오류는 전파한다.                                 |
| 공개 블로그의 Route Handler       | 백엔드의 상태 코드·본문·Content-Type을 전달한다. 204·205·304에는 본문을 붙이지 않는다. | 백엔드의 실패 응답도 같은 방식으로 전달한다.                                                       |
| 관리자 앱의 API 함수              | JSON을 읽고 필요한 모델로 변환한다. HTTP 204는 `undefined`를 반환한다.                 | HTTP 오류는 `Error`를 던진다. 인증된 요청의 401 처리에는 로그아웃과 로그인 페이지 이동이 포함된다. |

공통 응답 envelope를 자동으로 풀거나 런타임 스키마를 검증하는 계층은 없다. TypeScript 타입 선언만으로 실제 응답을 검증했다고 간주하지 않는다.

화면은 데이터 없음과 요청 실패를 구분한다. 게시글 상세의 `null`은 `notFound()`로 처리한다. 서버 캐시 경계를 지난 오류의 클래스 판별에 의존하지 않도록, 상태 코드에 따른 변환은 API 오류를 직접 받는 위치에서 수행한다.

## 서버 캐시

두 앱의 Next.js 설정에는 `cacheComponents: true`가 활성화되어 있다. 이 설정만으로 모든 데이터가 캐시되는 것은 아니다. 공개 블로그는 `api.server.ts`에 파일 단위 `"use cache"`와 `server-only`를 선언하고, 공개 조회 함수마다 `cacheLife`와 `cacheTag`를 지정한다.

| 조회 함수       | 재검증 간격 | 태그                                          |
| --------------- | ----------- | --------------------------------------------- |
| `getPosts`      | 60초        | `posts`                                       |
| `getPost`       | 60초        | `posts`, `post-`와 slug를 조합한 태그         |
| `getTags`       | 60초        | `tags`                                        |
| `getArticles`   | 60초        | `articles`                                    |
| `getAlgorithms` | 60초        | `algorithms`                                  |
| `getAlgorithm`  | 3,600초     | `algorithms`, `algorithm-`과 id를 조합한 태그 |
| `getStats`      | 60초        | `stats`                                       |

이 값은 `cacheLife`의 `revalidate` 설정이며, 해당 시간이 지나면 즉시 최신 화면을 보장한다는 뜻은 아니다. 검색 조건·페이지·slug·id는 해당 함수의 인자로 전달한다. 무효화 태그와 입력별 캐시 키를 혼동하지 않는다.

브라우저 요청을 받는 공개 블로그의 Route Handler에도 별도 캐시 정책이 있다. 태그를 지정할 수 있는 GET 요청에는 `fetch`의 60초 재검증을 적용하고, 나머지는 `no-store`를 사용한다. 이 정책과 Server Component의 캐시 정책을 함께 확인한다.

MDX 본문 렌더링과 Footer에도 명시적인 캐시 경계가 있다. 요청 시점에 결정되는 콘텐츠는 `Suspense` 아래에서 처리한다. 인증 토큰·쿠키·개인별 데이터는 공개 콘텐츠와 같은 공유 캐시에 넣지 않는다.

## 변경 요청과 캐시 갱신

공개 블로그의 Route Handler는 백엔드 변경 요청이 성공한 경우에만 `revalidateTag`를 호출한다.

| 변경 대상              | 갱신 대상으로 표시하는 태그           |
| ---------------------- | ------------------------------------- |
| 게시글의 조회수·좋아요 | 해당 게시글 태그, `posts`, `articles` |
| 알고리즘               | 해당 리소스 태그, `algorithms`        |
| 방문 기록              | `posts`                               |

현재 호출은 `revalidateTag`의 `"max"` 정책을 사용한다. 기존 캐시를 제공하면서 백그라운드에서 재검증할 수 있으므로, 변경 직후의 사용자 피드백을 서버 캐시 갱신에만 맡기지 않는다.

관리자 앱은 백엔드에 직접 쓰기 요청을 보낸다. 관리자 앱에서 게시글을 저장했다고 해서 공개 블로그의 태그를 즉시 무효화하는 연결은 현재 없다. 앱 간 즉시 갱신이 필요하면 별도 연동을 설계해야 하며, 그 방식은 TBD다.

## 브라우저 상태 관리

공개 블로그의 서버 캐시, TanStack Query 캐시, Jotai 상태는 서로 다른 역할을 맡는다.

- [ArticlesClient](../apps/web/src/components/articles-client.tsx)는 TanStack Query로 검색·태그·정렬·페이지별 조회 결과를 관리한다. 쿼리 키에는 이 조건들이 포함된다.
- 같은 파일의 조회 옵션은 `staleTime` 60초, 자동 재시도 없음, 이전 결과 유지로 설정되어 있다. 서버에서 전달한 초기 데이터는 기본 필터의 첫 페이지에만 사용한다.
- [QueryProvider](../apps/web/src/components/query-provider.tsx)는 QueryClient를 생성한다. 앱 전체에 공통 재시도 정책을 설정하고 있지는 않다.
- [게시글 반응 상태](../apps/web/src/store/post-metrics.ts)는 Jotai로 slug별 좋아요 수·선택 여부·요청 중 상태를 공유한다. 낙관적 갱신 후 실패하면 상태와 localStorage를 되돌린다.
- 관리자 앱은 현재 컴포넌트 상태와 Effect에서 API 함수를 호출한다. TanStack Query를 사용한다고 가정하지 않는다.

새 조회를 무조건 클라이언트 훅으로 옮기지 않는다. 공개 페이지의 초기 데이터는 기존 Server Component 경로를 먼저 확인하고, 사용자 조작 후 다시 조회해야 하는 데이터는 해당 클라이언트 상태 관리와 연결한다.

## 관리자 인증과 이미지 업로드

관리자 로그인은 `/api/auth/login`에서 받은 토큰을 localStorage의 `devblog_admin_token`에 저장한다. `adminFetch`는 이 토큰을 Authorization 헤더에 넣고, 401 응답을 받으면 토큰을 제거한 뒤 로그인 페이지로 이동한다.

[AuthGuard](../apps/admin/src/components/AuthGuard.tsx)는 브라우저에서 토큰의 존재 여부만 확인한다. 서버 권한 검증을 대신하지 않는다. HttpOnly 쿠키 인증이나 토큰 자동 갱신은 현재 구현되어 있지 않다.

게시글 관리 요청과 알고리즘 변경 요청은 관리용 API를 사용한다. 알고리즘 목록·상세 조회는 관리자 앱에서도 공개 API를 사용한다. 공개 블로그의 Route Handler는 관리자 Authorization 헤더를 전달하는 프록시가 아니다.

[PostForm](../apps/admin/src/components/post-form.tsx)의 이미지 업로드는 다음 순서로 진행된다.

1. 관리용 API에 파일명을 보내 서명된 업로드 URL을 받는다.
2. 브라우저에서 해당 URL로 파일을 PUT 요청한다.
3. 반환된 경로를 Supabase Storage의 `blog-images` 공개 URL로 변환한다.

[admin의 업로드 라우트](../apps/admin/src/app/api/upload/route.ts)도 존재하지만, 현재 PostForm은 API 함수를 통해 백엔드에 직접 서명 URL을 요청한다.

## API 변경 절차

1. 공개 조회인지, 사용자 반응인지, 관리자 작업인지 정하고 실제 호출 경로를 확인한다.
2. 해당 앱의 API 모듈에서 요청·응답 타입과 모델 변환을 함께 수정한다.
3. 공개 서버 조회를 추가하면 캐시 가능 여부, 재검증 간격, 태그를 정한다.
4. 변경 요청이 영향을 주는 목록·상세·클라이언트 상태를 확인하고 갱신 범위를 정한다.
5. 데이터 없음, 요청 실패, 인증 만료, 변경 성공·실패를 해당 경계에서 검증한다.

코드 변경과 검증 절차는 [프론트엔드 변경 가이드](frontend_clean_code_guide.md)를 따른다.
