# Next.js 예외 처리, 로깅 및 보안

## 예외 처리

- 예외를 빈 `catch`로 무시하거나 `console.log`만 출력하고 종료하지 않는다.
- 단순히 화면에 기술적인 오류 메시지만 표시하지 않는다.
- 예상 가능한 오류와 예상하지 못한 오류를 구분해 처리한다.
- 사용자가 현재 상황을 이해하고 다음 행동을 수행할 수 있도록 오류를 처리한다.
- 입력 오류는 해당 필드 가까이에 원인과 해결 방법을 표시한다.
- 페이지 또는 영역 오류는 오류가 발생한 범위에서 복구 방법과 함께 표시한다.
- 재시도로 해결될 수 있는 오류에는 재시도 수단을 제공하되 중복 요청이 발생하지 않도록 한다.
- 오류 발생 후에도 사용자가 입력한 값과 작업 맥락을 가능한 한 유지한다.
- 경로 렌더링 오류는 `"use client"`를 선언한 `error.tsx`로 격리한다. 같은 세그먼트의 layout 오류는 상위 경계에서 처리하고, 루트 오류용 `global-error.tsx`에는 `<html>`과 `<body>`를 포함한다.
- Server Action의 입력 검증 등 예상 가능한 실패는 직렬화 가능한 반환 상태로 전달한다. 예상하지 못한 예외는 오류 경계에서 처리한다.
- 존재하지 않는 리소스에는 `notFound()`와 `not-found.tsx`를 사용한다. `redirect()`와 `notFound()`의 제어 흐름 예외를 일반 `catch`에서 삼키지 않는다.
- 이벤트 핸들러 및 별도 비동기 요청의 실패는 해당 Action/Mutation/핸들러에서 처리한다. 모든 비동기 오류를 `error.tsx`가 잡는다고 가정하지 않는다.

## 오류 상황별 기본 대응

- 비로그인 상태에서는 로그인 페이지로 이동하고 로그인 후 기존 페이지로 복귀할 수 있도록 한다.
- 로그인 복귀 URL과 사용자 입력으로 만든 이동 경로는 허용된 내부 경로인지 검증해 open redirect와 스크립트 URL 실행을 막는다.
- 권한 부족 시 접근 불가를 안내하고 사용자가 접근 가능한 안전한 페이지로 이동할 수 있도록 한다.
- API 요청 실패 시 사용자 친화적인 안내와 재시도 수단을 제공한다.
- 네트워크 오류 시 연결 상태와 재시도 방법을 안내한다.
- 데이터가 없을 경우 빈 화면 대신 의미 있는 빈 상태 UI를 표시한다.
- 저장 실패 시 입력값을 유지한 채 재시도할 수 있도록 한다.
- 일부 데이터만 실패한 경우 전체 화면을 막지 않고 실패한 영역에 대체 UI를 제공한다.
- 예상하지 못한 렌더링 오류에는 Error Boundary와 복구 UI를 제공한다.

## 로깅

- 오류 수집 도구가 설정되어 있다면 개인정보, 인증 정보, 요청 본문을 제거한 뒤 필요한 문맥과 함께 기록한다.
- 사용자에게 내부 오류 메시지, 서버 스택 트레이스, 토큰, 요청 헤더를 노출하지 않는다.
- 인증 토큰, 개인정보, API 응답 전체를 콘솔이나 오류 메시지에 출력하지 않는다.

## 보안 및 환경 변수

- 환경 변수는 `process.env`로 읽는다. `NEXT_PUBLIC_` 접두사 변수는 클라이언트 번들에 공개되고 빌드 시 값이 고정될 수 있다고 간주한다.
- `NEXT_PUBLIC_` 변수와 `next.config.ts`의 `env`에 비밀번호, 비밀 키, 서버 전용 토큰을 저장하지 않는다. 서버 비밀값을 props, Action 반환값, API 응답으로 전달하지 않는다.
- `.env*`는 해당 Next.js 앱 루트에서 관리한다. 실제 비밀값을 커밋하지 않으며 예시 파일에는 변수 이름과 안전한 예시만 둔다.
- 서버 전용 인증/데이터 모듈에는 `import "server-only"`로 경계를 표시한다. 서버와 브라우저에서 공유하는 기존 모듈은 사용처를 확인하고 서버 전용 부분을 분리한 뒤 적용한다.
- Server Action과 Route Handler는 직접 호출할 수 있는 서버 진입점으로 취급한다. 전달된 ID, FormData, 쿠키와 헤더를 신뢰하지 않고 요청마다 인증과 리소스 권한을 확인한다.
- 새 인증 흐름은 서버에서 검증하는 `HttpOnly`, `Secure`, 적절한 `SameSite` 쿠키를 우선 검토한다. 기존 JWT 전달 방식은 별도 마이그레이션 없이 임의 변경하지 않는다.
- 사용자 입력을 HTML로 직접 삽입하지 않는다.
- `dangerouslySetInnerHTML`은 신뢰할 수 있고 정제된 데이터에만 제한적으로 사용한다.
- MDX는 코드를 실행할 수 있으므로 신뢰하지 않는 사용자 입력을 그대로 컴파일하거나 실행하지 않는다.
- 외부 링크를 새 탭으로 열 때는 필요한 보안 속성을 함께 적용한다.
- 클라이언트의 권한 검사는 UX 보조 수단으로만 사용하고 보안이 클라이언트 검사만으로 보장된다고 가정하지 않는다.
