# 테크니컬 라이팅

기술 문서의 목표는 감동이나 새로운 관점이 아니라 **독자가 문제를 해결하고 목표를 이루도록 돕는 것**이다. 정보를 빠르고 정확하게 전달하는 데 집중한다.

출처: [토스 테크니컬 라이팅 가이드](https://technical-writing.dev) (CC BY-NC-SA 4.0). 아래는 그 원칙을 요약·재구성한 것이다.

MDN이나 React 문서처럼 규모가 큰 문서뿐 아니라 한 페이지짜리 README, 블로그 포스트에도 그대로 적용한다.

## 적용하지 않는 경우

회고, 에세이, 감상 위주의 글에는 적용하지 않는다. 이런 글은 정보 전달이 목적이 아니다. 모든 원칙은 권장 사항이므로 상황에 맞게 판단하고, 어긴다면 근거를 짧게 남긴다.

## 실행 절차

### A. 새 문서를 쓸 때

순서를 지킨다. 유형이 정해지지 않으면 구조를 짤 수 없고, 구조가 흔들리면 문장을 다듬어도 소용없다.

1. **문서 유형 정하기** → 검증: 독자의 목표를 한 문장으로 쓸 수 있고, 4가지 유형 중 하나를 골랐다
2. **정보 구조 만들기** → 검증: 목차만 읽어도 흐름이 이해되고, H4(`####`)가 없다
3. **문장 다듬기** → 검증: 아래 문장 체크리스트를 문단마다 통과한다

유형별 구조와 템플릿은 [references/doc-types.md](references/doc-types.md)를 읽고 그대로 채운다.

### B. 이미 쓴 문서를 검토할 때

인수로 받은 경로(`$1`)의 문서를 읽고, **구조 → 제목 → 문장** 순서로 검토한다. 구조를 먼저 보는 이유는, 섹션을 통째로 옮기거나 나누면 문장 단위 지적이 무의미해지기 때문이다.

1. 유형이 내용과 맞는지 확인한다 (튜토리얼인데 API 옵션을 나열하고 있지 않은지)
2. 구조 체크리스트를 적용한다
3. 문장 체크리스트를 문단마다 적용한다

## 검토 결과 형식

지적 하나는 다음 세 요소로 이루어진다.

- **위치**: `파일:줄` 또는 섹션 제목
- **문제**: 어긋난 원칙 이름 + 왜 문제인지 한 문장
- **수정안**: 고쳐 쓴 실제 문장 또는 구조

수정안은 "구체적으로 쓰세요" 같은 조언이 아니라 복사해서 붙일 수 있는 결과물이다. 원칙 이름만 나열하고 수정안을 빼면 검토가 아니다.

여러 원칙이 한 문장에 겹치면 지적을 나누지 말고 하나의 수정안에 모두 반영한다.

## 구조 체크리스트

| 원칙                        | 확인할 것                                                                                                                                  |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 한 페이지에서 하나만 다루기 | 핵심 주제가 하나인가. `####`(H4)가 나오면 문서를 나눌 신호다. 여러 개념을 소개해야 하면 개요 페이지를 따로 만들고 링크한다                 |
| 가치를 먼저 제공하기        | 첫 단락이 기능 나열이나 도입 배경이 아니라 "이걸 적용하면 무엇이 좋아지는지"인가                                                           |
| 개요 빠트리지 않기          | 제목 바로 아래, 본문 전에 개요가 있는가. "이 문서를 읽으면 무엇을 할 수 있는가"에 답하는가                                                 |
| 예측 가능하게 하기          | 같은 수준의 제목이 같은 패턴인가. 기본 개념 → 사용법 → 예제 → 심화 순인가. 코드보다 설명이 먼저 나오는가. 같은 개념을 같은 용어로 부르는가 |
| 자세히 설명하기             | 새 개념이 처음 나올 때 한두 문장으로 정의했는가. 값에 단위·범위·조건이 붙어 있는가                                                         |

제목은 핵심 키워드를 넣고, 30자 이내로, 평서문으로 쓴다(`!`, `?` 금지). 같은 수준의 제목은 어미를 통일한다(`~하기`로 맞추면 `~하세요`, `~ 유지`를 섞지 않는다).

더 자세한 Do/Don't 예시는 [references/structure.md](references/structure.md)에 있다.

## 문장 체크리스트

| 원칙                     | Don't                                                                     | Do                                                                       |
| ------------------------ | ------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 주체는 독자(개발자)      | 이 라이브러리는 데이터베이스 초기화를 수행해요                            | 이 명령어를 실행하면 데이터베이스를 초기화할 수 있어요                   |
| 능동형으로               | 설정이 완료되어야 합니다                                                  | 설정을 완료하세요                                                        |
| 한 문장에 하나의 생각    | 버튼을 클릭하면 다음 단계로 이동하게 되며, 이후 작업을 진행할 수 있습니다 | 버튼을 클릭하면 다음 단계로 이동합니다. 이동 후 작업을 이어서 진행하세요 |
| 메타 담화 제거           | 앞에서 설명했듯이, 결론적으로 이 설정이                                   | 이 설정이                                                                |
| 명사 대신 동사           | 코드 최적화 진행 후 배포 수행이 필요합니다                                | 코드를 최적화한 후 배포하세요                                            |
| 모호한 표현 금지         | 일부 브라우저에서 동작하지 않을 가능성이 있습니다                         | Internet Explorer에서는 동작하지 않습니다                                |
| 누가·무엇을·어디에       | 파일을 업로드하면 자동으로 저장됩니다                                     | 사용자가 파일을 업로드하면 서버에 자동으로 저장됩니다                    |
| 수치와 기준 명시         | 데이터가 많을 때는 성능이 저하될 수 있습니다                              | 데이터가 10,000건을 넘으면 응답 시간이 1초 이상 걸립니다                 |
| 참조 맥락 밝히기         | `apiKey`로 인증합니다                                                     | 1단계에서 `apiKey`에 저장한 키로 인증합니다                              |
| 불필요한 한자어 제거     | 로그 파일을 삭제하는 작업을 수행합니다                                    | 로그 파일을 삭제합니다                                                   |
| 번역체 명사형 풀기       | 사용자 인증 처리가 완료된 후 접속 설정 진행이 가능합니다                  | 사용자를 인증한 후 접속하도록 설정할 수 있습니다                         |
| 용어 일관성              | 추가 / 첨부 / 넣기를 섞어 쓴다                                            | 하나의 문서에서 "업로드"로 통일한다                                      |
| 공식 표기 사용           | K8, 자바스크립트                                                          | 쿠버네티스(Kubernetes), JavaScript                                       |
| 약어 첫 등장 시 풀어쓰기 | SSR을 지원합니다                                                          | SSR(Server-Side Rendering)을 지원합니다                                  |

도구나 기술 자체의 동작을 설명하는 문장은 예외다. "Impression 로그는 두 가지 방식으로 동작해요"처럼 주체가 기술이어도 된다.

외래어 표기는 맞춤법보다 업계 관행을 우선한다(예: `프런트엔드`가 아니라 `프론트엔드`).

더 자세한 Do/Don't 예시와 연습 문제는 [references/sentences.md](references/sentences.md)에 있다.

## 여러 페이지로 된 문서

문서가 여러 페이지가 된다면 유형별로 디렉토리를 나누고, 관련 문서끼리 크로스링크를 건다. 기본 구조는 [references/doc-types.md](references/doc-types.md)의 "문서 트리" 절에 있다.

## 흔한 실수

- **구조를 건너뛰고 문장부터 다듬는다.** 섹션 순서가 뒤엉킨 문서는 문장을 고쳐도 읽기 어렵다. 구조 먼저다.
- **개요 대신 배경 설명을 쓴다.** "이 기능은 2019년에 도입되었고..."는 개요가 아니다. 독자가 얻을 가치가 개요다.
- **코드를 먼저 붙이고 설명을 뒤에 쓴다.** 독자가 코드를 먼저 해석해야 한다. 설명 → 코드 순으로 배치한다.
- **모호함을 정중함으로 착각한다.** "~할 수도 있습니다"는 배려가 아니라 정보 부족이다. 조건을 아는 만큼 명시한다.
- **유형을 섞는다.** 튜토리얼에 API 옵션 표를 넣지 말고 레퍼런스로 분리해 링크한다.
